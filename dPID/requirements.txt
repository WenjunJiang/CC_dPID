# gradient_accumulation_steps into the per-device batch is only gradient-neutral
# if the loss is divided by the accumulation count exactly once, which is an
# emergent property of how Trainer and Accelerator interact. The condition moved
# between releases - 4.51.3 has
#   `if not model_accepts_loss_kwargs and compute_loss_func is None`
# whereas 5.9.0 has
#   `if (not model_accepts_loss_kwargs or num_items_in_batch is None) and ...`
# - so it cannot be assumed. Verified empirically on 5.9.0 + accelerate 1.13.0
# (the deployed pair), and also on 5.9.0 + 1.12.0 and 4.51.3 + 1.12.0: the same
# effective batch gives a median relative gradient difference of 1.5e-5 (fp32
# summation-order noise) versus 0.41 for a genuinely different effective batch.
# In all three, Trainer leaves the division to Accelerator.backward.
#

# by the resolver - it records the pair the check was run against. The code does
# not depend on it either: verify_repack_equivalence() re-runs the check at
# startup and falls back to the unrepacked split if it ever fails.
